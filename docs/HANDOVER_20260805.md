## 1. ★★ 必改：遙測要用 `pushadd_to_gateway`，不可用 `push_to_gateway`

這是今天家族其他四個專案全部踩到的坑，你的專案 CLAUDE.md 當時還沒寫，
**請檢查你的程式碼有沒有用到 `push_to_gateway`，有的話改成 `pushadd_to_gateway`**。

### 為什麼

`push_to_gateway()` 是 **HTTP PUT ＝ 整組取代**。而契約是
「`scrapy_last_success_timestamp_seconds` 僅在成功時設」——
所以**失敗那次**推上去的那組裡沒有它，PUT 會把**前一次成功的時間戳一併洗掉**。

而存活告警是：

```promql
time() - scrapy_last_success_timestamp_seconds{...} > 門檻
```

序列不存在時，這個式子對**空向量**求值 → **永遠不會燒**。

也就是說：**爬蟲失敗這件事本身，會讓偵測它失敗的告警消失。**

### 這不是理論

今天 `adsb` 從 15:00 起每小時失敗，Pushgateway 上只剩 `last_run` 與
`log_errors=1`，`last_success` 整個不見，**兩小時內沒有任何告警**，
是人工去查資料庫才發現的。

### 實測對照（對正式 Pushgateway，用拋棄式 grouping key）

```
push_to_gateway    (PUT )  推成功→有 last_success，再推失敗→ ❌ 不見了
pushadd_to_gateway (POST)  推成功→有 last_success，再推失敗→ ✅ 還在
```

### 改法

只要改函式名，參數完全一樣：

```python
from prometheus_client import CollectorRegistry, Gauge, pushadd_to_gateway
...
pushadd_to_gateway(url, job=JOB_NAME, registry=reg,
                   grouping_key={'instance_id': instance, 'spider': 'loadcurve'},
                   timeout=5)
```

POST 的代價是舊指標名不會被清掉（某次推了之後再也不推的指標會留著舊值）。
**這是刻意接受的取捨**：留一個過期的值，遠好過整組告警靜默失效。

專案 CLAUDE.md 的「遙測（必做）」段落已補上這條，記得一併同步過去。

## 2. 要決定：`area_gen` / `area_load` 只有抓取當下那一個時間點

這是我從資料看出來的，**不是錯誤，但會影響前端怎麼畫**。

| kind | 不同時間點 | 涵蓋範圍 |
|---|---|---|
| `fuel` | **104** | 00:00–17:10（全天，10 分鐘一點）|
| `area` | **104** | 00:00–17:10（全天，10 分鐘一點）|
| `area_gen` | **3** | 16:10、16:20、17:10 |
| `area_load` | **3** | 16:10、16:20、17:10 |

原因很清楚：`loadfueltype.csv` 與 `loadareas.csv` 是**當日累積檔**，每次抓都拿回一整天；
但各區發電/用電那份只回報**當下**，所以每跑一次只會多一個時間點。

**後果**：每小時跑一次的話，`area_gen`/`area_load` 的解析度是**每小時一點**，
而 `area`/`fuel` 是每 10 分鐘一點。中間漏掉的 5 個時間點**永久取不回來**
（那份來源沒有歷史）。

**建議（請你判斷後回覆，不要自己改排程）**：

- **方案 A（建議）**：維持每小時，前端把 `area_gen`/`area_load` 當作
  **「各區現在發多少／用多少」的即時數字**，不要畫成連續曲線。
  畫成曲線會讓人以為中間那 50 分鐘是平的，那是假的。
- **方案 B**：改成每 10 分鐘抓一次才能補齊。但那是 6 倍的請求量，
  對台電官網的爬取自律要重新評估，我不建議為了這個支線資料這樣做。

★ 無論選哪個，**都不可以把沒抓到的時間點補 0 或內插**——未知≠零。
